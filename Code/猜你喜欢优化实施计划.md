# “猜你喜欢”优化实施计划

> 目标：在不修改 A/C/B 输出格式、不修改 D 前端组件与页面的默认边界内，先消除确定性漏召回和错误排序，再提升排序区分度、结果规模、画像时效性与推荐理由准确性。
>
> 执行方式：供后续自动化编码任务按阶段顺序直接执行。每阶段必须先测试、再进入下一阶段；不得覆盖工作区已有未提交改动。

## 1. 范围与约束

### 1.1 默认允许修改

- `Code/server/routes/recommend.ts`
- `Code/server/data/userMemory.ts`
- `Code/server/data/topicBoilerplate.ts`
- `Code/server/data/mentorRetrieval.ts` 中 D 侧共享的可信来源与排序辅助逻辑
- 新增或更新 `Code/server/**/*.test.ts`
- D 模块及根目录说明文档

### 1.2 默认禁止修改

- `Code/src/components/`
- `Code/src/pages/`
- A 后端、C 数据构建脚本、B 星图功能代码
- `candidate_id` 形式及四模块输出结构
- 用户已有未提交改动

以下工作必须单独取得用户授权后才能执行：

- 冷启动 onboarding 的按钮、跳转或引导页面；
- 结构化推荐理由标签的前端展示；
- 修改 `paper-claw-master/data_scripts/build_rag.py` 的生成逻辑；
- 修改 A 后端的候选 schema 或评分契约。

## 2. 完成标准

完成后应同时满足：

1. `topics_source=1` 和当前可信的 `topics_source=3` 均可进入推荐候选池；`0/2` 不可进入。
2. 已收藏和已标记“不感兴趣”的导师不出现在“猜你喜欢”结果中。
3. 真实主题不会因为“长度超过 40”或包含“专注/主要研究”等正常表达而被整条误删。
4. 推荐排序不再只依赖 92/75.44 两档分数和 `candidate_id`。
5. 匹配多个画像方向的导师优先于只匹配一个方向且其他条件相同的导师。
6. `evidence_coverage`、实际证据置信度/来源级别/新鲜度进入次级排序；重复证据不能刷高排序。
7. 论文信号只使用已核验论文信息，并作为弱次级信号，不能压过主题关系等级。
8. 默认最多返回 6 位导师，可配置但硬上限不超过 12。
9. 每位导师的 `explanation` 只引用其实际命中的画像方向，不再统一引用画像前 3 项。
10. 近期检索拥有保留配额，不会被 8 项长期兴趣完全挤掉。
11. 空画像行为明确、可测试，不允许静默返回伪个性化热门导师。
12. D 现有测试、生产构建和新增推荐测试全部通过。

## 3. 自动化执行协议

### 阶段 0：建立安全基线

1. 读取根 `AGENTS.md`、`CLAUDE.md`、`Code/AGENTS.md`。
2. 记录 `git status --short` 和相关文件 diff。
3. 把已有修改视为用户资产；不得 reset、checkout、覆盖或顺手格式化无关文件。
4. 运行：
   - `npm test`
   - `npm run build`
5. 若 `tsx` 因本机 `uv_os_get_passwd/ENOMEM` 失败，只允许使用临时运行时补丁绕过；补丁不得提交，测试后立即删除。
6. 若基线存在真正的项目测试失败，先报告并判断是否与本任务相关；不得在不明原因下继续大范围修改。

阶段产物：基线测试结果、当前 RAG 候选数、`topics_source` 分布、工作区保护说明。

### 阶段 1：建立“猜你喜欢”专属测试层

新增推荐路由/纯排序逻辑测试，避免继续只依赖检索单元测试。优先把候选池筛选、画像聚合、排序和截断抽成无数据库副作用的纯函数，以便用固定 fixture 测试。

必须覆盖：

- 空画像；
- 单一长期方向；
- 8 项长期方向 + 2 项近期方向；
- 多方向命中覆盖；
- source 0/1/2/3；
- 收藏、取消收藏、不感兴趣；
- DIRECT 与 ADJACENT；
- 同分候选；
- 重复证据；
- 长主题、带句号的主题、网页模板噪声；
- 结果上限与稳定排序；
- 每位导师理由引用其真实命中项。

阶段门禁：新增测试先能复现当前缺陷，再进入实现阶段。

### 阶段 2：先修确定性漏召回

#### 2.1 统一 D 侧可信来源口径

把可信主题来源判断集中成一个共享函数或常量，推荐和检索都调用同一处：

```text
trusted topic source = {1, 3}
```

当前语义：

- `0`：无方向；
- `1`：官网 profile 方向；
- `2`：旧版未核验论文回填，禁止；
- `3`：官网无方向时，由作者实体已核验平台的论文标题经受控词表回填。

D 侧增加不变式测试：source 3 候选必须有 `paper_identity_verified=true`、非空 `paper_platforms`，并绑定可信的论文方向证据。若当前数据不满足，不得直接放宽候选池，应停止并报告数据问题。

不在本阶段修改 C 的构建逻辑；C 侧进一步强化生成不变式属于需授权的跨模块工作。

#### 2.2 修复 D 加载时的主题误删

调整 `topicBoilerplate.ts`：

1. 对包含 `。；;` 的长描述先做保守分段；
2. 对每个片段独立判断模板噪声；
3. 删除固定的“长度超过 40 即整条丢弃”策略，替换为可解释的模板/联系方式/论文行规则；
4. 保留英文长研究方向、带括号方向和含“专注/主要研究”的有效主题；
5. 去重并保持原始顺序。

固定回归样例至少包括：

- “凝聚态物理。专注于发展……”必须保留“凝聚态物理”；
- 数值计算、开放量子系统等长英文方向不能因长度被删除；
- 招生须知、版权、邮编、网址、导航项仍必须删除。

阶段门禁：已确认的“催化化学”和“凝聚态物理”漏召回消失，且模板噪声测试不回退。

### 阶段 3：消除收藏反馈闭环中的错误排序

1. `dislikedIds` 继续作为硬排除。
2. `favoriteIds` 改为候选池硬排除，不再参与置顶比较器。
3. 收藏导师的方向仍可作为低权重画像信号，但单独标识为 `favorite` 来源：
   - 最多保留 2 项；
   - 每位收藏导师最多贡献 1 项非泛化方向；
   - 不允许覆盖近期检索配额；
   - 与成长/个人兴趣重复时只保留一份。
4. 删除“收藏优先于相关分数”的排序逻辑。

阶段门禁：已收藏导师和不感兴趣导师均不返回；同方向的未收藏导师仍可被推荐。

### 阶段 4：重建画像配额与自然语言记忆

把画像信号分层保存，不再过早合并成无来源的 `core[]`：

- 长期方向：最多 4 项；
- 最近检索：最多 2 项；
- 收藏推导：最多 2 项；
- 总量最多 8 项。

建议权重：

- 近期检索：1.20；
- 长期方向：1.00；
- 收藏推导：0.60。

权重必须集中配置，禁止散落魔法数字。

修复自然语言记忆抽取，至少保证：

```text
“找网络空间安全学院做大模型、愿意招本科生的老师”
→ 画像主题“大模型”，而不是“做大模型”
```

在不改前端的前提下继续从原始历史查询解析；若未来要保存结构化 query contract，需要另行设计数据库/前端契约。

阶段门禁：即使长期方向已有 8 项，最近两次有效检索仍各有机会参与推荐。

### 阶段 5：建立分层排序，避免破坏 `matchScore` 语义

不要直接把论文数、收藏状态等揉进用户看到的主题匹配分。保留：

- `matchScore`：主题关系强度；
- 内部排序特征：画像覆盖、证据质量、论文支持；
- 如需暴露 `rankingScore`，必须作为可选新增字段，不能替换 `matchScore`。

推荐采用分层比较器，顺序如下：

1. `DIRECT` 优先于 `ADJACENT`；
2. `matchScore` 降序；
3. 加权画像覆盖分降序；
4. 去重后的证据质量分降序；
5. 已核验论文支持分降序；
6. `candidate_id` 仅作最终稳定性兜底。

#### 5.1 画像覆盖

聚合每位导师实际命中的全部画像项，不再只保留最高分匹配。覆盖分应使用阶段 4 的来源权重，并按总可用画像权重归一化。

#### 5.2 证据质量

由候选实际绑定的 `BoundEvidence` 计算，至少考虑：

- `confidence`；
- `query_relevance`；
- `source_level`；
- `freshness`；
- 不同来源数量。

先按 `evidence_id` 去重，再聚合。现有 `evidence_coverage` 可以复用，但不能仅凭原始证据条数加分。

当前 `evidence_confidence=95/45` 是通道可信性的二值标记，不得继续冒充细粒度证据质量。应保留兼容字段或重新命名，同时新增由真实证据计算的内部质量值。

#### 5.3 论文支持

- 只使用身份已核验的论文数据；
- 对数量做对数/封顶处理；
- 有年份时优先考虑近期研究活跃度；
- 仅作最后一级弱平分项；
- 不允许 ADJACENT 因论文多而越过 DIRECT。

阶段门禁：同一主题的多位导师不再全部仅按 ID 排序；匹配更多画像且证据更强者稳定前移。

### 阶段 6：Top-K 与多样性

1. 服务端最终默认返回 6 位；
2. 允许通过受控环境变量配置为 1–12；
3. 截断必须发生在完整排序之后；
4. 在不降低 DIRECT 优先级的前提下做轻量多样性约束：
   - 默认同一院系最多 2 位；
   - 若不足 6 位，可放宽约束补足；
   - 不得用低相关候选强行补满。

阶段门禁：任何画像最多返回配置数量；结果不足时真实返回不足，不添加伪匹配。

### 阶段 7：纯后端修复导师级推荐理由

在聚合结构中保留：

- 实际命中的画像词；
- 信号来源（长期/近期/收藏）；
- `matchedTerms`；
- 最强证据摘要。

继续写入现有 `Advisor.explanation` 字符串，不要求前端改动。例如：

```text
与你最近关注的“大模型”和长期方向“自然语言处理”直接相关；官网研究方向明确提及“大语言模型”。
```

禁止：

- 所有导师统一引用画像前 3 项；
- 理由提及该导师实际未命中的方向；
- 把论文数量描述成主题相关性。

结构化理由标签属于可选前端阶段，不在默认自动化范围。

### 阶段 8：冷启动策略

默认后端行为：

- 空画像返回空推荐；
- 响应增加可选、向后兼容的 `needsOnboarding: true`；
- 不偷偷用论文数或热门导师伪装个性化结果。

如用户授权前端改动，再实施：

- 空态显示“选择研究方向”主按钮；
- 跳转个人资料研究方向设置；
- 提供 3–5 个方向的轻量选择流程。

若比赛演示要求新账号立即看到内容，应由产品明确选择“引导式冷启动”还是“标注为热门导师的非个性化 fallback”，不得混淆两者。

### 阶段 9：完整验证

#### 自动化测试

- D 全部现有测试；
- 新增推荐单元测试和路由测试；
- `npm run build`；
- 使用固定 fixture 验证 source 3、清洗、收藏、负反馈、画像配额、排序、Top-K、解释；
- 使用当前 RAG 做只读集成诊断，但不要把易变化的全库数量作为脆弱断言。

#### 推荐效果回归集

至少覆盖：

- 大语言模型；
- 推荐系统；
- 计算机视觉；
- 机器人；
- 量子计算；
- 催化化学；
- 碳材料；
- 蛋白质结构；
- 凝聚态物理；
- 一个明确无结果的窄方向；
- 两个 AND 多方向查询；
- 八项混合画像。

记录每个案例的：返回数、DIRECT/ADJACENT 分布、同分规模、画像覆盖、证据质量、最终顺序、排除原因。

#### 人工检查

对被 D 清洗删除的 93 条主题生成审阅清单，分类为：

- 确认模板噪声；
- 确认有效主题；
- 需要人工判断。

报告必须使用精确口径：`93 条被删 / 涉及 44 位 / 5 位清空 / 已确认误删案例数 / 待标注数`，不得把“涉及”写成“全部受到负面影响”。

## 4. 推荐提交拆分

工作区当前有用户未提交改动，自动化任务默认只修改文件、不自行提交。若用户之后明确要求提交，建议拆成：

1. `fix(recommend): align trusted topic sources and topic cleaning`
2. `fix(recommend): exclude saved mentors and reserve memory quotas`
3. `feat(recommend): rank by profile coverage and evidence quality`
4. `feat(recommend): cap and diversify recommendation results`
5. `fix(recommend): generate mentor-specific explanations`
6. `test(recommend): add route and ranking regression coverage`
7. `docs(recommend): document source semantics and evaluation results`

每个提交只包含对应阶段文件，不混入用户既有改动。

## 5. 自动停止条件

出现以下任一情况必须停止并报告，不得自行扩大范围：

- 需要改 `Code/src/components` 或 `Code/src/pages` 才能继续；
- 需要修改 A/C/B 功能代码或输出 schema；
- source 3 数据不满足身份核验不变式；
- 相关文件中的用户改动与计划实现发生无法安全合并的冲突；
- 新排序使已知 DIRECT 候选被 ADJACENT 候选越过；
- 清洗修复导致模板噪声大规模重新进入 tags；
- 构建或测试出现无法确定归因的新失败；
- 需要数据库破坏性迁移或重置现有用户数据。

## 6. 最终交付报告模板

自动化执行完成后必须报告：

1. 修改文件与对应阶段；
2. 修复前后案例对比；
3. 测试数量、通过/失败情况；
4. 当前默认 Top-K；
5. source 0/1/2/3 的处理规则；
6. 收藏、负反馈、冷启动的最终行为；
7. 尚未执行的前端或跨模块事项；
8. 工作区原有改动是否完整保留。
