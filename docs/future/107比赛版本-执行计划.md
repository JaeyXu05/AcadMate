## 0. 命题对齐：107 比赛版要证明什么

按 `107_从比赛到长期开源项目_新版规划` §06，本档定位：

> **证明 Verifiable Research Mission（可验证的研究任务闭合环）**

必须有：

- Mission Workspace（任务工作台）
- 结构化 Event
- Evidence（证据）
- Review / Retry 可见
- 统一输入 Unified Intake
- Mission Replay
- 真实 Demo 转折

**最关键的诊断**（出自 `_open_research_clean.md` §13）：

> *"你后端明明有 Plan、Event、Evidence、Review、Retry、Resume，为什么用户只看到一串 thinking 文本？"*

代码核实结论：

- **A 后端其实已经具备** typed state（`WorkflowState`）、EvidenceLedger、
  ReviewDecision（5 枚举值 + 顺序检查）、RetryController（返工循环）、
  event_bus + `/events`、state_version + resume——这些"可信 Agent"骨架已写好。
- **但 D 代理把它们压扁了**：`Code/server/routes/agent.ts` 用硬编码的 `EVENT_HINT`
  字符串表把 A 的结构化事件 flatten 成 `thinking` 文本；`ReasoningChain.tsx` 只是按换行拆字符串。
- 现事件词汇表里**没有** `review_failed` / `retry_started` / `evidence_updated` /
  `claim_conflict` / `approval_required` 这类语义事件，而它们正是 Demo 转折的素材。

**一句话定位**：107 版 = 把「A 已存在的可验证运行时」变成「前端看得见的 Mission 工作台」+ 一条含真实转折的 Demo 闭环。

### 组一｜共有数据底座（P0，A 牵头）

所有新 UI 共同依赖的 schema，必须先定义，否则前端无从着手。

| # | 内容 | 说明 |
|---|---|---|
| 1.1 | **RuntimeEvent 语义化**：把 event_bus 现有粗粒度事件扩成带结构化 payload 的语义事件 | 新增 `stage_started / tool_called / source_opened / artifact_created / claim_added / evidence_added / conflict_found / review_failed / retry_started / replan_started / approval_required`；payload 带 `stage / agent / message_id / trace_id / version` |

### 组四｜真实 Demo 转折（P0，压轴）

按规划 §07 的 8 步 Demo 路径，核心是：

> **"某导师一开始排名高 → Auditor 发现关键研究方向只有旧证据 → 触发 RESEARCH_AGAIN → 补证据 → 排名和 3D 图同时变 → 最后给一句『最大缺口』"**

这不是炫技动画，而是组一（事件）+ 组三（Timeline/Workspace）的自然产物：
只有事件真的语义化、证据真的带 freshness、Review 真的能触发返工，这个转折才真实可信。
它同时验证 Multi-Agent / Evidence / Review / Retry / Event Stream / 3D / Human-in-loop 七个点。

## 4. 关键风险与依赖

- **A 的语义事件 schema 未冻结前，D 的 Timeline 只能做占位**——M1 是硬前置。
- **Demo 转折的"真实性"依赖 C 的 stale-evidence 素材**：若库里没有"关键方向只有旧证据"的真实案例，
  Demo 会退化成人工脚本，失去"可验证"的说服力。
- **离线兜底**：全程保证 A 不可达 / 无模型 key 时 Demo 仍可跑（现有 stub 兜底逻辑要保留并适配新事件协议）。
- **ID 稳定**：`candidate_id` 四模块一致，本档改动不得破坏（见现有约定）。
